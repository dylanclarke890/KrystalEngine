# Krystal.Booey

Booey is the engine's web engine: HTML, CSS, the DOM, SVG, MathML and canvas 2D, for everything the engine shows as UI (menus and HUDs, pages on in-world surfaces, editor tooling, and shipped tools such as launchers). It's a C++ port of WebKit's WebCore, from the clone at `C:\Users\dylan\repos\WebKit` (commit `300e80c70fd3`), and keeps WebCore's structure: most classes, files and algorithms have an upstream counterpart with the same name in PascalCase. Krystal.UI draws it through Render2D (see `docs/gfx/OVERVIEW.md`).

The specs are the reference for behaviour; WebKit is the reference for structure. Where Booey differs from either, or from Chrome, it's recorded in `DIFFERENCES.md`; known bugs and gaps are in `KNOWN-ISSUES.md`. Fine-grained open work is marked in the code with `// FIXME:` comments (upstream's own FIXMEs are kept too).

## Scope

**In:** the DOM, HTML (elements, forms, the parser, dialogs, popovers, `<details>`, commands, custom elements defined in C++), CSS (parsing, the cascade, every standard property, container queries, anchor positioning, the CSSOM and CSSOM View), layout (block, inline, flex, grid, table, positioning, floats, ruby), painting and compositing, scrolling, transitions, animations and the Web Animations API, editing and selection, mouse, keyboard, pointer, touch, pen and gamepad input, IME composition, drag and drop, links, navigation and session history with the back/forward cache, resize and intersection observers, SVG (the legacy render tree), MathML Core, canvas 2D, engine textures in pages, and right-to-left and bidi text.

**Later:** remote pages (a network loader with HTTP, caching, cookies, origins and CORS; until then the host fetches remote data and pushes it into pages); video and audio (`HTMLMediaElement` with a host media player, the default controls and text tracks); an inspector, as a Krystal.UI panel over the DOM, CSS and layer tree (its hooks were left out: the CSS parser's observer, the resolver's CSSOM wrappers, forced pseudo-classes and the instrumentation points); the rest of the Typed OM.

**Not planned:** JavaScript and scripting in general (bindings, the JavaScript-only parts of the specs such as `handleEvent`, IDL callbacks, HTML element constructors and scripting in the parser), realms and global objects other than the window, origins and `document.domain`, trusted types, Content Security Policy and `nonce`, policy-controlled features, workers and service workers, the APIs in WebCore's `Modules/` (WebRTC, IndexedDB, WebAuthn, payments and the like), WebGL and WebGPU, content extensions and plug-ins, iframes and a frame tree, printing and pagination, accessibility, and the iOS and macOS code. With no global objects, `DocumentFragment` is constructed with a document. Where a missing feature changes a specification algorithm, the call site is marked `SPEC-VIOLATION` (global objects, trusted types, service workers, origins, Content Security Policy, browsing contexts and Web IDL).

**Dropped on purpose:** `-webkit-`/`-apple-` features, WebKit's non-standard features and legacy aliases (properties, pseudo-classes and elements, at-rules, SVG 1.1 features SVG 2 removed). The exceptions are the non-standard properties the engine itself uses and the `-webkit-` and `-epub-` aliases of standard properties, which are still kept (see `DIFFERENCES.md`). Everything in a standard is kept, even where Booey has no use for it yet, so it's easy to wire up.

Without scripting, the DOM's callbacks are C++: listeners are `Func`s owned by `EventListenerHandle`s, observer callbacks (`MutationCallback`, `ResizeObserverCallback`, `IntersectionObserverCallback`) are `Func`s, and the window has the spec's `Window` interface for C++ callers.

## Working on Booey

When fixing or reviewing code that mirrors upstream, read the upstream file first, and keep the two in step unless `DIFFERENCES.md` says otherwise. Comments in the code don't mention WebKit or upstream except in FIXMEs; upstream comments carried over are kept.

**Naming.** Functions and methods are PascalCase, with British spelling in identifiers (`serialize` is `Serialise`). Public data members of plain structs, `static constexpr` trait members included, are PascalCase; when a member shares its type's name (`CompositeOperation CompositeOperation`), write the type as `boo::X` inside the struct. Class constants (`Color::red`) and container-protocol methods (`size`, `get<I>`, `at`, `data`) keep upstream's names. A method named after a type would hide it, so it's renamed (`colorSpace()` is `Space()`, `quad()` is `GetQuad()`). The typed colour maths (`platform/graphics/Color*.h` other than `Color`, `ColorBlending`, `ColorSerialization` and `ColorHash`) lives in Krystal.Core under `Colour/`, in namespace `krys`, spelled "Colour" (`ColourSpace`, `ColourComponents`, `ConvertColour`, `PackedColour`), with `BlendMode` and `GradientSpreadMethod`, so Render2D can use it without Booey; the CSS `Color` class and the names of CSS concepts (`css::ColorType`, `ResolvedColor`, `InterpolateColors`) keep the spec's spelling.

**Won't port.** Remove these at the include site rather than stubbing them: `TextStream` debug dumping, `TZoneMalloc` (`WTF_MAKE_TZONE_ALLOCATED`), `wtf/Forward.h` (include the headers), `NoVirtualDestructorBase`, the CSS parser's observer (`CSSParserObserver`, `CSSParserObserverWrapper`) and the inspector entry points, `DestinationColorSpace` and `PlatformColorSpace` (use `ColorSpace`), and IPC types (`*DataForIPC`).

**MSVC.** `TimingFunction`, `TransformOperation`, `FilterOperation`, `PathOperation` and `StyleImage` compare through a non-virtual `operator==` over a virtual `Equals`, because MSVC finds C++20's reversed `operator==` candidates ambiguous.

### The build

Booey compiles as a unity build: CMake joins its sources into batches of 16. Without it, the Debug static library outgrows the 4 GB a static library can hold.

- **File-local names share a batch.** Anonymous-namespace and `static` helpers, constants and types, and `using namespace` directives at namespace scope, are visible to the files after them in the batch: two files defining the same helper fail to compile, and a directive can make a name ambiguous elsewhere. Look for a shared helper before writing one (`text::CodePointAt` and friends in `Text/CodePointIterator.hpp`, `infra::StringAlgorithms`, `css::SkipExactly` in `ParserIdioms.hpp`), and put a new shared helper where upstream keeps it or beside the type it works on.
- **Qualify instead of `using namespace`** at namespace scope (`mq::Feature`); function-scope directives are fine.
- **Clashing helpers under upstream's names** stay, and their sources compile on their own (`SKIP_UNITY_BUILD_INCLUSION` in `Krystal.Booey/CMakeLists.txt`: `WidthIterator.cpp`, `ComplexTextController.cpp`, `TextBoxPainter.cpp`, `RenderListMarker.cpp`, and the generated sources).
- **Include what each file uses.** A file can compile only because an earlier file in its batch included something; building once with `-DCMAKE_UNITY_BUILD=OFF` shows what's missing.
- Release is supported: variables only debug assertions use are `KRYS_MAYBE_UNUSED`, and MSVC builds with `/bigobj` for `InterpolationWrapperMap.cpp`.
- Code generators in `Krystal.Booey/codegen/` (`css_properties.py`, `css_pseudo_selectors.py`, and the user agent style sheets in `codegen/user-agent-style-sheets/`) produce the property, pseudo-selector and interpolation tables from `css-properties.json` and `css-pseudo-selectors.json`.
- Every header and source is listed in `Krystal.Booey/CMakeLists.txt`; a file that isn't listed isn't built.

## By area

### DOM

- The DOM is single-threaded and written from the specification's algorithms (`MutationAlgorithms`, `ElementAlgorithms`, `TextAlgorithms`, `SlotAlgorithms`, `MutationObserverAlgorithms`) rather than ported from WebKit. SVG properties are plain `RefCounted`, not thread-safe.
- There is no `TreeScope`. Its state (style scope, adopted style sheets, custom element registry, `ActiveElement`) lives on `DocumentOrShadowRoot`, a base of `Document` and `ShadowRoot`; a node's tree scope is found by walking to its root with `TreeQueries::Root`.
- Because change steps run after a change and nothing keeps copies of classes, the ID or form control state (the selector checker reads attributes), style invalidation wraps the changes themselves: `ElementAlgorithms` wraps each attribute store in one invalidation scope, and `MutationAlgorithms`/`TextAlgorithms` wrap each inserted, removed or moved node and each text change in a `ChildChange` scope. `Style/PseudoClassStateInvalidation` maps an attribute or child change to the elements and pseudo-class states it may flip (`:link`, `:checked`, `:default`, `:indeterminate`, `:disabled`/`:enabled`, `:read-only`/`:read-write`, `:required`/`:optional`, `:placeholder-shown`, `:lang()`, `:dir()`). A state that may flip is invalidated as if it flips, so there is some over-invalidation; `:lang()` and `:dir()` use `AnyValue`.
- `StyledElement` sits between `Element` and `HTMLElement`/`SVGElement`/`MathMLElement` and owns the inline style (there is no shareable element data). The `style` attribute is synchronised lazily: a CSSOM change only marks it dirty (`NodeFlags::StyleAttributeIsDirty`), and `Element::SynchronizeAllAttributes()` writes it back, with no change steps or mutation record. `Element::_attributes` is read directly in many places, so code that reads it must call `SynchronizeAllAttributes()` first.
- Hover, focus and active state live in `UserActionElementSet` (a map of raw pointers; elements leave it when removed). `Document::SetFocusedAndActive` (true by default) stands in for the frame's focused/active state: `:focus` and relatives only match while it is set, and `hasFocus()` returns it.
- `Document` has a real URL and base URL: `about:blank` until the host calls `SetURL`, a frozen base URL from the first `<base href>`, and a cached `CssParserContext()` invalidated when the base URL or quirks mode changes. `CompleteURL` is UTF-8 only.
- A parsed `<style>` is a style sheet candidate from insertion but only creates its sheet once its text is complete: the tree builder begins parsing children before inserting the element, and the sheet owner reads `Element::IsFinishedParsingChildren()`.
- Documents are freed. Nodes hold their document without owning it (the document counts referencing nodes via `IncrementReferencingNodeCount`/`DecrementReferencingNodeCount`), containers release their children when destroyed through a deletion queue (`RemoveDetachedChildren`), and `Document::RemovedLastRef` clears what retains nodes before freeing; Krystal.Core's `RefCounted` can resume from zero (`ResumeFromNoRefs`) for this. Because `RemoveDetachedChildren` doesn't run the removing steps, `RemovedLastRef` takes elements out of the top layer first. `View` and `LocalFrame` free the old document on a new page load. `MemoryCache::Singleton` is a `NeverDestroyed`, so resources it lists are never deleted under it.
- Mutation observers, transient registered observers and `slotchange` are written from the DOM specification; `slotchange` bubbles at the slot when observers are notified. Character data offsets, damage offsets in inline layout and rendered text offsets are UTF-8 byte offsets throughout.
- Event listeners added from C++ with `EventTarget::AddEventListener(type, Func<void(Event &)>, options)` return a move-only `EventListenerHandle` that removes its listener on destruction, assignment or `Remove()` (`Release()` leaves it to the target). The handle holds weak pointers and removes by identity, so a listener already removed (`once`, aborted signal, dead target) is left alone. `AddEventListener<TEvent>` takes the event type explicitly and calls back only for events that are a `TEvent`. `EventTarget` has `DidAddEventListener()`/`DidRemoveEventListener()` hooks that the event target algorithms call, so handles, signals and event handler attributes count towards `LocalDOMWindow`'s gamepad listener count.
- Custom elements are C++ behaviour objects. A definition is a `CustomElementInterface` (name, `CustomElementFactory`, observed attributes, `CustomElementOptions` for `disabledFeatures` and `formAssociated`). An element stays the `HTMLMaybeFormAssociatedCustomElement` it was created as, and the factory creates a `CustomElement` (the host's class, with the lifecycle callbacks as virtual methods) that the element holds, both on synchronous creation and on upgrade; a late definition keeps element identity. A factory returning null, or a behaviour for another element, counts as a constructor that threw (`HTMLUnknownElement` in the `failed` state, or a failed upgrade). `FormAssociatedCustomElement` is the listed, validated half of the element.
- `CEReactionsScope` pushes an element queue around the C++ members the IDL marks `[CEReactions]`; `CustomElementReactionStackSuspension` takes the stack away while Booey calls host code (listeners and the callbacks themselves). Editing commands scope their changes (`DoApply`, undo, redo), so reactions run after the command's changes. Reactions enqueued with no queue on the stack go to the backup element queue (a static queue processed in a microtask of `EventLoop::Current()`).
- Registries are stored per document, shadow root and element as the specification has it. A document gets its global registry when it becomes a frame's current document; `View::DefineCustomElement` (Krystal.UI) keeps a definition and defines it in every document the view loads, before parsing (via the client's `DispatchDidClearWindowObject` hook), and in the current document.
- Observers (`ResizeObserver`, `IntersectionObserver`) are made from C++ with `Create(document, callback[, init])`; native observers are told apart by `CreateNativeObserver`. Resize observations loop deeper each round with layout between; undelivered ones report an `error` event at the window ("ResizeObserver loop completed with undelivered notifications."). No `device-pixel-content-box`, as upstream.
- Image maps have no tree scope maps by name or by `usemap`: an image's map is the first `map` in its tree whose `id` or `name` matches, and a map's image is the first image in its tree that uses it.

### HTML parser

- The tree builder (`HTMLTreeBuilder`) creates elements synchronously, outside fragment parsing, following the specification's element queues and *will execute script*; fragment parsing creates upgrade candidates that upgrade on insertion.
- XML-based documents (`image/svg+xml`, `application/xml`, XHTML) go through `XMLDocumentParser` over libxml2, chosen by MIME type.

### HTML elements and forms

- Dialogs, popovers and close watchers follow the specification's model. `html::CloseWatcher` is made from C++ with `CloseWatcher::Create(document, {.Signal = ...})`, the window's `CloseWatcherManager` groups watchers by user activation, and Escape closes the newest group first.
- Custom commands (`--name`) are delivered as `CommandEvent`s at the `commandfor` element for C++ to handle. Popovers' invokers are implicit anchors.
- `<details>` has a user agent shadow tree (summary slot, content slot styled by `::details-content`, skipped with `content-visibility: hidden` while closed); `name` groups are exclusive accordions.
- Form control state is saved and restored by `FormController` with the history item (not for reloads, password fields or `autocomplete=off`); form-associated custom elements get `FormStateRestoreCallback` with the `Restore` mode.
- `:checked`, `:default`, `:indeterminate` and related pseudo-classes are computed from element state that follows the HTML specification (checkbox and radio `Checked()`, option `Selected()`, the nearest ancestor form's default button).
- Date, colour, file and select controls delegate their choosing to the host (colour picker, date picker, select popup, file chooser) through client interfaces such as `ColorChooserClient`; the control reads the host's answer, and the host hides its picker before telling the client.

### CSS parsing and CSSOM

- The rule model (`CSS/Rules/Rule.hpp`, an `XRule` class per rule type) is the internal representation, as `Value` is for CSS values. CSSOM wrappers (`CSSStyleSheet`, `CSS*Rule`) are created from it by `Rule::CreateCSSOMWrapper`. `CSSParser` is upstream's merged `CSSParser`/`CSSParserImpl` and produces this model; there are no inspector observers.
- Generated code: `codegen/css_properties.py` (property parsing, shorthand functions, `IsExposed`, initial values) and `codegen/css_pseudo_selectors.py` (selector enums, gperf maps, `UserAgentParts`) read filtered JSON copies (`codegen/css-properties.json`, `codegen/css-pseudo-selectors.json`). CMake passes `--defines=ENABLE_DARK_MODE_CSS,ENABLE_VARIATION_FONTS,ENABLE_APPLICATION_MANIFEST`; other defines are left off and `conditional` isn't supported (every standard pseudo is generated).
- Serialisers (selector text, shorthands, media/container queries, rules) live with the layer that owns them and are tested with parsing. Everything is UTF-8: the tokenizer, selector maps and fast paths take `CSSOMStringView`, and non-ASCII names don't match gperf maps.
- Feature flags: a feature in a published specification (or editor's draft) is always on, whatever its upstream status. `Settings` flags remain only for features without a specification or that are WebKit's own (`color-layers()`, `transform-style: separated`, `::thumb`/`::track`, `spring()`), embedder features (`-apple-color-filter`, system `appearance` values, `appearance: attachment`), internal UA-sheet parsing (`cssInternalAutoBaseParsingEnabled`) and the media text track display quirk; `ParserContext` keeps exactly those flags.
- Non-standard, `-webkit-`, `-internal-` and legacy properties and pseudo-classes are dropped (the selector parser rejects them), apart from the non-standard properties the engine uses, the `-webkit-` form control parts (user agent sheets only) and the `-webkit-`/`-epub-` aliases of standard properties; standard features are kept even when unsupported.
- The user agent style sheets are checked in as preprocessed copies (`codegen/user-agent-style-sheets/`, non-Apple platform, MathML enabled) and embedded by a codegen step that minifies them. Rules whose every selector uses a non-standard pseudo (`-webkit-` form control parts, `:-webkit-autofill*`, `-internal-` document pseudo-classes) are removed; the `-webkit-` declarations the sheets use are kept.
- Media features read a `MediaEnvironment` (`CSS/Queries/MediaEnvironment.hpp`) that the host fills in with `LocalFrame::SetMediaEnvironment`, standing in for the frame, page, settings, theme and screen. It holds effective values: forced accessibility settings and theme preferences collapse to one field each and the host applies its own overrides. The `pointer`, `hover`, `any-pointer` and `any-hover` features read the pointing devices set with `View::SetPointingDevices()`.
- `matchMedia()` is on `Document`. `MediaQueryList` change events are reported when the host calls `Document::EvaluateMediaQueriesAndReportChanges()` (for example after `SetMediaEnvironment`); `matches` keeps its result until then. `MediaQueryList` isn't an `ActiveDOMObject` and has no `onchange`.
- Font-relative units in media queries resolve against the document element's user agent style, with the css-values-4 fallback metrics (ascent = font size, line spacing 1.2em, `ex` 0.5em, `ch` 0.5em, `ic` 1em) when there is no font data. Container query size features evaluate as unknown without a principal box; `style()` container queries evaluate fully.
- Constructed `CSSStyleSheet`s use the document's base URL and parser context (default settings).
- Generated builder and extractor code (`Style/BuilderGenerated.cpp`, `Style/ExtractorGenerated.cpp`) goes in the build's codegen directory (not committed) and is compiled with `/bigobj`.

### Style (cascade and computed values)

- Computed style follows upstream's structure: `Style::ComputedStyle` with the `rendering/style` data groups, generated `ComputedStyleProperties`/`RenderStyleProperties` accessors (`Get` prefix when the name would hide a type), `RenderStyle` wrapping `ComputedStyle`, and the builder and extractor generated from `codegen/css-properties.json`.
- `Settings` is not upstream's roughly 710 preferences: it holds only what Booey reads. It is ref-counted and set by the host; documents share `Settings::Default()` unless given their own via `Document::SetSettings` (which schedules a full style rebuild; sheets already parsed aren't reparsed), and documents a document creates (`DOMImplementation`, clones, fragment parsing) share its settings. Values upstream reads from `Settings` that Booey doesn't model use upstream's defaults in code (popovers and view transitions on, vertical form controls, switch control off, `hiddenUntilFoundEnabled` on, layer-based SVG engine off, MathML Core and `math-depth` on).
- Style invalidation is split: direct invalidations (insertion, removal, inline style, presentational hints, `<body>` link colours, table cell borders, shadow root attach, slot assignment) plus the selector-based invalidators (`Invalidator` and the `Class`/`Id`/`Attribute`/`PseudoClass`/`ChildChangeInvalidation` classes) hooked to the DOM change steps. The host or event loop calls `Document::UpdateStyleIfNeeded`; there is no style recalc timer.
- A document needs a full style rebuild at first (`_needsFullStyleRebuild` starts true); `Document::InitialContainingBlockStyle()` is created on demand from `ResolveForDocument` if the document hasn't resolved yet. Style resolution holds back styles (so no renderers) while head style sheets load; `RenderBlocking` is kept up to date but nothing reads it.
- `Style::Update` and other `CheckedPtr` targets must be heap-allocated (no stack exemption in `CheckedPtr`). `RenderStyle` and `ComputedStyle` aren't `CheckedPtr` targets, so `TransformResolver` and `CachedMatchResult` hold plain references or pointers.
- The theme is Adwaita-based; system colours are semantic, so default black text and borders record their colour in paint dumps.
- Anchor positioning is interleaved with layout: style resolution and layout alternate for anchor-positioned boxes until anchors are found and laid out. `position-try-fallbacks` options are tried in `position-try-order`, starting with the last successful option (recorded in the rendering update's resize observations step, forgotten when the fallbacks or order change, the box goes, or a `@position-try` rule changes). Anchor-positioned boxes follow their default anchor's scrolling by a layer transform without layout, and are laid out again to choose another option or hidden by `position-visibility: no-overflow` once pushed out of their containing block. The rendering update has a snapshotted scroll offsets step.
- Content visibility: `hidden` and skipped `auto` contents are skipped in layout, painting and hit testing but laid out for geometry queries (`TreatContentVisibility*AsVisible` layout options); scrolling to skipped content makes it relevant; relevancy is on screen, focused, selected, or holding a top-layer element. `contain-intrinsic-size: auto` uses the document's native `ResizeObserver` last remembered sizes.
- `:state()` matches `CustomStateSet` with style invalidation; `:target` follows the document's target element.

### Animations

- CSS animations, transitions and the Web Animations model (`WebAnimation`, `AnimationTimeline`, `DocumentTimeline`, `KeyframeEffect`, `CSSAnimation`, `CSSTransition`, `StyleOriginatedAnimation`) are upstream's, run on the host's event loop time (`View::Update(now)`). The page's animations step runs "update animations and send events", and the document timeline schedules rendering updates while animations run.
- Time is the window's: the timelines controller's live time is the window's `NowTimestamp()` (the host's time since its time origin), and the frozen time of an update is its `FrozenNowTimestamp()`, both in seconds. A document without a frame or window has no current time.
- Pending animations get their start time from the last time the timelines controller cached (`_lastCachedCurrentTime`), not the cache itself: the host runs the event loop once per frame (timers before tasks), so the 15 ms clearance timer would otherwise always fire first and leave animations pending forever.
- An animation is created in the rendering update that resolves its style and starts at once (phase active while pending, hold time zero), so `animationstart` fires in that update.
- The Web Animations API is used from C++: `KeyframeEffect::Create(document, target, keyframes, options)`, `Element::Animate()`, `GetAnimations()` (with `subtree`) on `Element`, `Document` and `ShadowRoot`; CSS animations stop following what C++ overrides; `DocumentTimeline` takes an origin time. Animations take times as numbers or `CSSNumericValue` (`CSSNumberish`), and `TimelineRangeOffset`/`TimelineRangeValue` use the Typed OM numeric values.
- `ScrollTimeline::Create(document, options)` and `ViewTimeline::Create(document, options)` are made from C++ or from style (`scroll()`, `view()`, `scroll-timeline`, `view-timeline`, `timeline-scope` via the document's `StyleOriginatedTimelinesController`); timelines are brought up to date after the rendering update's resize observations.
- The accelerated halves of `KeyframeEffect`, `KeyframeEffectStack`, `DocumentTimeline`, `WebAnimation`, `BlendingKeyframes` and `Styleable` hand transform and opacity animations to graphics layers (see Compositing).
- A document leaving its frame stops its timers; suspended documents (back/forward cache) pause animations, `requestAnimationFrame` callbacks and layout.
- SMIL (`SVG/Animation/SMILTimeContainer.cpp`) runs on its own timer rather than the rendering update.
- The golden `animations` uses animations paused at negative delays, so neither it nor Chrome's capture depends on capture time.

### Layout

- Layout is WebKit's: `RenderBlock`, `RenderBlockFlow`, `RenderFlexibleBox`, `RenderGrid`, `RenderTable` and the rest of the render tree, plus the `layout::` formatting contexts (inline, block, flex, grid) reached through `layout_integration`. Every block container whose children are inline uses the inline formatting context. Flex and grid containers use the formatting context where `CanUseFor` allows it and fall back to `RenderFlexibleBox` and `RenderGrid` otherwise. Tables always use the `RenderTable*` classes.
- `layout::Box`es are owned by the block container's line layout and built by `BoxTreeUpdater`. Tests that inspect layout trees must release line layouts first (`DetachLineLayout` in `LayoutTestUtils.hpp`).
- Offsets into text everywhere in layout and rendering are UTF-8 byte offsets (inline items, breaking positions, soft line breaks, `TextUtil` ranges, damage positions). `BreakablePositions` (the line breaking fast paths in front of ICU, with its generated ASCII pair table) steps by code points and sends supplementary characters to ICU. The bidi paragraph is built in UTF-8 and handed to ICU `ubidi` as a UTF-16 copy whose run ends are mapped back to bytes.
- Side tables that upstream keeps in weak hash maps (overriding sizes, percent-height descendants, out-of-flow descendants, counter maps, first-letter remaining text, the flex and grid caches, the scroll info transaction) are keyed by renderer address. Entries are removed in `WillBeDestroyed` or cleared explicitly, so a reused address cannot be mistaken for the old box.
- `CheckedPtr` needs the complete type when dereferenced, so `RenderObject::LayoutBox`, `Box::Parent` and `Box::RendererForIntegration` are out of line; `layout::Box` checked pointers are made with `ShareCheckedPtr`.
- Static `QualifiedName`s and the `TextBreakingPositionCache` singleton are `NeverDestroyed`, because layouts hold entries past function-local static destruction.

### Painting

- Booey paints into a display list through `boo::GraphicsContext` (state savers, `NullGraphicsContext`, `display_list::DisplayList`, `Recorder`). `LocalFrameView::Paint` translates by the scroll position and clips to the visible rect, and layers paint in stacking order (backgrounds, negative `z-index`, foreground phases, outline, normal flow, positive `z-index`), with opacity and blend modes as transparency layers and transforms, rounded overflow clips and `clip-path` as clips. Krystal.UI replays the list on Render2D.
- Recording keeps upstream's state handling: state changes are recorded just before the next drawing item (colour and thickness changes inline, anything else as the whole state), and a change back to what was last drawn records nothing. Lists dump as text in upstream's format, and the Booey paint tests compare dumps.
- Border, outline, shadow, text decoration and list marker painters are upstream's, with its fast paths (a uniform solid border as one even-odd path, a single plain shadow on an opaque background drawn on the fill). Skip-ink needs `Font::PathForGlyph`.
- Generated images (gradients, border images) tile as upstream does: rendered once into an `ImageBuffer` cached at the context's scale and filled as a pattern, so hard stops antialias consistently. A gradient constant along one axis is shrunk to a one-unit strip (`adjustParametersForTiledDrawing`), and `Image::DrawTiled` with `RoundTile` fits `round(W / w)` tiles as the specification does.
- Pattern fills and strokes use `Pattern` and `SourceImage` with a pattern case in `SourceBrush`; Krystal.UI renders the tile to a texture and paints it with Render2D's `ImagePattern2D`.
- Filters paint in upstream's "graphics context" mode: `TransparencyLayerContextSwitcher` begins a transparency layer per filter function (the last outermost), clipped to what it paints and composited with a `GraphicsStyle` (colour matrix, Gaussian blur, drop shadow) that Krystal.UI hands to Render2D as a layer filter. `Page::PreferredFilterRenderingModes` always returns the graphics context. The filter effects of `DrawFilteredImageBuffer` are kept as platform-neutral data, and `FilterGraph2DBuilder` builds a Render2D `FilterGraph2D` (one node per effect over pooled float textures); software appliers are not ported because Booey cannot rasterise on the CPU. A graphics style's blur radius is the CSS blur radius (twice the standard deviation).
- Because Render2D can only blur inside the clip, a repaint inside a layer whose filter moves pixels grows to everything the filter paints (`RenderLayer::AbsoluteFilterRepaintRect`), such layers are not repaint containers, and moving or changing one repaints its old and new halo (`RenderLayerModelObject`).
- Masks: `RenderBox::paintMaskImages` paints mask layers and `mask-border` into a transparency layer composited with `destination-in` (or straight into a composited mask layer). A luminance mask `ImageBuffer` is marked as one (the display list backend marks it) rather than converted pixel by pixel, and Krystal.UI renders it through a luminance-to-alpha layer. A masked layer's group is clipped to the layer, so its intermediate surface leaves out its filters' outsets.
- `clipToImageBuffer` mask clips open a layer under the clip; the buffer's texture is drawn over it with `DestinationIn` when the clip ends.
- Stroke hit testing and stroke bounds (`Path::StrokeContains`, `StrokeBoundingRect`) ask a host strategy, `PathStrokeStrategy`; Krystal.UI implements it with Render2D's `PathStroker` (`PathStrokerStrategy`, installed by `View`), and Booey's own tests use a stand-in. `Path::Contains` is a winding number test with curves flattened.
- When the page does not composite (no graphics layer factory, as in the Booey tests), the frame view collects damage as a region in view coordinates (`LocalFrameView::RepaintContentRectangle`, `InvalidateRect`, `RepaintEntireView`); the host takes it once a frame (`HasDamage`, `TakeDamage`), where upstream tells a host window immediately. Repaints are in the render view's coordinates. `Repaint`, loads, style recalculation and layout timers just schedule a rendering update, and scrollbar invalidation does nothing. A host must paint after an update that asks for one (`View::NeedsPaint`), because a backing waiting for a whole repaint ignores further repaints until it has been painted.
- Krystal.UI's `View::Paint` on that path groups damaged rects (merging two when their bounds waste no more than their own area, or while there are more than 8), records each group, replays them under clips into a second texture and copies them into the page texture (`BlitTexture`). Corners within a sixteenth of a pixel of circular are drawn as circles (`ToCircularRoundedRect`) to avoid path-mask fills. Scrolling there is a pixel move: the view records how its painted contents moved (`ScrolledContents`, `ScrollHostContents`, `TakeScrolledContents`), moves the damage with it and paints only what comes into view plus fixed objects' old and new rects.
- Without compositing every layer paints into the window, so `paintsWithTransparency`, `shouldPaintMask` and `shouldApplyClipPath` do not consult a backing, `canPaintTransparencyWithSetOpacity` is false and `fixedBackgroundPaintsInLocalCoordinates` is false.
- The render theme is GNOME's Adwaita (namespace `krys::boo::adwaita`). `DrawControlPart` display list items draw with the part's default factory and Krystal.UI replays them on its graphics context. `outline-style: auto` draws the themed ring (a 2-unit ring outside the path with round joins, the inside clipped out; around boxes with a border radius it follows the corners via `PathWithShrinkWrappedRects`); Skia's backend would draw none without the theme.
- Highlights: `Highlight` and `HighlightRegistry` (usable from C++ via `Document::HighlightRegistry()`) are painted with `::highlight()`; text fragments use `::target-text` or the theme's annotation colours, with positions worked out at each rendering update.
- The top layer is rendered by `RenderLayer::TopLayerRenderLayers` and `EstablishesTopLayer`. Top-layer elements are positioned in the viewport (`position` other than `fixed` computes to `absolute`); their layers, and their `::backdrop`s' (generated by `RenderTreeUpdater::GeneratedContent::UpdateBackdropRenderer`, only in the top layer), are the view's last, above any `z-index`, and a `::backdrop` hit-tests to its element.

### Compositing and scrolling

- Compositing is on when the host gives the page a graphics layer factory (`ChromeClient::GetGraphicsLayerFactory`) and attaches the root through `ChromeClient::AttachRootGraphicsLayer`. The render view's layer is then the root, with the viewless-port structure (overflow controls host > frame clipping > frame scrolled contents > content root). `Page::UpdateRendering` ends with `FinalizeRenderingUpdate`, which flushes compositing state in place of upstream's drawing area. `GraphicsLayer::Create` needs the host's factory.
- Booey side: `RenderLayerCompositor`, `RenderLayerBacking`, `RenderGeometryMap`, `LayerOverlapMap`, `LayerAncestorClippingStack`. A backing holds its sharing layers weakly (`List<WeakPtr<RenderLayer>>`, skipping destroyed ones) while the compositor passes a `ListHashSet<RenderLayer *>` of live layers. All compositing triggers are allowed, overflow scrolling composites whenever the page composites (`asyncOverflowScrollingEnabled`), and fixed-position compositing follows compositing.
- Krystal.UI side (`Krystal.UI/Compositing/`, adapted from TextureMapper): `GraphicsLayerTextureMapper` records changes and commits them to its `TextureMapperLayer` on flush, including the bounds origin (`BoundsOriginChange`); `TextureMapperLayer` composites transforms, opacity, clips, masks, backdrops, filters and groups; `ui::TextureMapper` draws with the frame's `Renderer2D`; `TextureMapperTiledBackingStore` tiles layers; `BitmapTexture` and `BitmapTexturePool` hold textures, and the pool releases textures unused for 180 frames. There is no retained single page texture and no separate damage-rect path; `View::NeedsPaint` is true while the page changed or composited animations run.
- `ui::TextureMapper` draws clips (`BeginClip`) as rounded-rect clips and groups (`BeginGroup`) as Render2D layers carrying a `LayerFilter2D`, opacity and blend mode; a mask mode applies a mask layer to its group. An intermediate surface (flattened group, filter, mask) is a Render2D layer, which finds its own bounds. Part of a texture is painted into a pooled surface and copied over it.
- Tiles cover what is visible of a layer and as much again around it, are kept until half a tile beyond that, and are sized as the coordinated-graphics port sizes GPU tiles (viewport-wide or half, a quarter of its height, at least 256 px). Each tile paints only its dirty rect by replaying the layer's recorded display list.
- A transform, opacity or filter change on a composited layer whose filters the compositor draws only recomposites it (`RenderElement::AdjustStyleDifference`); changes that start or end a stacking context or containing block still lay out. An effect that runs completely accelerated stops ticking the page's style each frame. `TextureMapperAnimation::Resume` takes the time, so hosts and tests control it.
- Backdrop filters: a layer with `backdrop-filter` composites and is a backdrop root. `TextureMapperLayer` paints its backdrop before the layer, clipped to the border box's rounded rect, as a group with the filters into which the backdrop root's subtree is painted again, up to the layer. The backdrop root is the nearest ancestor with opacity, a mask or filters, else the root.
- Canvases are composited as upstream's `USE(COMPOSITING_FOR_SMALL_CANVASES)` has them, with no area threshold for canvases or their 3D transforms. A `<canvas>` whose context is GPU-based (`"krystal-texture"` or an accelerated `"2d"`) gets its own layer whose contents are a display delegate (`GraphicsLayerContentsDisplayDelegate`); changes redisplay the layer without repainting the page. `GraphicsLayer::SetContentsDisplayDelegate` does nothing in Booey, and the host's layers show the delegate's platform layer and keep it alive while shown. When painted instead (snapshots, drag images), the texture is an `ExternalImage` drawn with no copy.
- Composited scrolling: overflow boxes that scroll their overflow get scroll container and scrolled-contents layers, with scrollbars in layers of their own; scrolling moves the scroll container's bounds origin and repaints nothing but newly visible tiles and the scrollbar. Fixed elements that paint something composite for their position under an anchor layer that the compositing update after each scroll moves; sticky boxes inside a composited scroller composite (`isAsyncScrollableStickyLayer`) with an overlap extent that is the union of their positions. Sticky boxes stuck to the view do not composite. The compositor fills the scroll corner layer with the view's background before painting it, since the theme draws no corner. Anchor scroll adjustment is done as a transform on the layer without a layout.
- Sticky positioning is upstream's: `StickyPositionViewportConstraints` and `RenderBoxModelObject`'s sticky offset (constraining rect, enclosing clipping box, containing block's content box) join the in-flow offset, `offsetLeft`/`offsetTop` and geometry mapping.
- `LocalFrameView` is itself the `ScrollableArea`, with the scrolling and scrollbar halves of upstream's `ScrollView` folded in (Booey has no widgets). Scrollbars come from `ScrollbarTheme::Theme()`, the Adwaita theme, drawn through `GraphicsContext`; they have no track, so a box's background shows through, and the view fills the scrollbar area with the root's background colour over the base background (`LocalFrameView::PaintScrollbarsBackground`; the root's background images stop at the scrollbars, FIXME). A held scrollbar track or button repeats after 250 ms, then every 50 ms, until the thumb reaches the mouse or the end. `scrollbar-gutter` reserves space as layout already did.
- Wheel scrolling: `wheel` fires at the element under the mouse, then, unless cancelled, scrolls the nearest enclosing box that can scroll that way, then the view, passing boxes at their end unless `overscroll-behavior` stops it.
- Page scale is applied by the frame view's conversions, the render view's transform, the compositor, hit testing, `elementFromPoint`, `devicePixelRatio` and the visual viewport. The page scale is saved and restored with the scroll position in `HistoryItem::PageScaleFactor()`.
- Animated images pause when their renderers cannot see the new frame and wait on the `RenderView`; `LocalFrameView::ViewportContentsChanged` (after layout, scrolling, resize) resumes the ones now in view.

### Text and fonts

- Fonts are bundled and found with no host setup: Liberation Sans (the default and last-resort font, always registered as family "Liberation Sans"), Noto Sans Arabic (unhinted build, `FontDatabase::BundledArabicFace`) and STIX Two Math (`FontDatabase::BundledMathFace`, found by `font-family: math` through `CSSFontSelector`'s known math fonts). `codegen/bundled_fonts.py` embeds them. Registered faces come first; system fallback then tries Liberation Sans, Noto Sans Arabic and STIX Two Math in that order. Hebrew comes from Liberation Sans. Tests measure with Ahem (`Krystal.Booey.Tests/data/fonts/`).
- The host adds more fonts with `FontDatabase` (`AddFontFile`, `AddFontDirectory`, `AddFontData`); `Page`/`View::AddFontDirectory` registers a directory's `.ttf`, `.otf`, `.ttc` and `.otc` files for every page. Generic families (`serif`, `sans-serif` and so on) resolve from the document's `Settings` (`FontGenericFamilies`, per script) and are unset by default, so they fall through to Liberation Sans.
- A document creates its font selector on first use. Changing the document's settings bumps the selector's version and restyles. A selector whose settings define generic families or prefer pictograph fallback is never "simple", so cascades from documents with different settings do not share fonts.
- `Krystal.Text` (`krys::text`) holds `FreeTypeFace`, `FontFileData`, `FaceStyle` and `HbUniquePtr`. Booey (shaping, font selection) and Render2D (rasterising) share one face per font file. Faces are unsized: Booey measures in font units and Render2D makes its own FreeType size objects (`FontFace2D`), so sizes never change under another user. `FaceStyle` reports the font's own weight, width and italic flag, from which Booey builds `FontSelectionCapabilities` (`CapabilitiesOfFace`). Shaping stays in Booey (`FontCascade`, `ComplexTextController`); there is no shaper outside it.
- Booey's `Font` holds platform data containing a `text::FreeTypeFace`. Display-list glyph items keep a `Ref` to the `Font`, glyph IDs and advances, and replay turns advances into positions. Krystal.UI's `FontFaceCache` keeps one `FontFace2D` per FreeType face plus synthetic bold and oblique.
- Render2D draws text through `FontFace2D` and `GlyphAtlas`. FreeType renders glyph bitmaps (8-bit coverage, or premultiplied RGBA for colour glyphs) into R8 and RGBA atlas pages, keyed by face id, glyph, size, subpixel quarter and the transform's linear part. Each pen is placed through the transform into target pixels and snapped (`GlyphAtlas::SnapPen`). Under a uniform positive scale glyphs are rasterised at the scaled size with no transform (so hinting applies); under other transforms at the size under the transform's linear part.
- A glyph is drawn as a pixel-aligned instance of atlas texels, sampled nearest: coverage as a mask (`Textured | Mask`, with the paint's colour or gradient), a colour glyph as a premultiplied image (white at the paint's alpha; gradients do not tint it). Glyphs on a page share a batch.
- Text past `Renderer2D::LargeGlyphSize` (256 target pixels per em), glyphs the atlas has no room for, and stroked text are filled from outlines (`FontFace2D::GlyphPath`) through the mask atlas, reusing the mask when the glyph moves by whole pixels. Faces whose only glyphs are bitmaps are excluded. Vertical text is rotated a quarter turn about its anchor.
- Text shadows draw for the whole run first from the glyphs' own bitmaps, as Skia does. A blurred shadow is the atlas's blurred glyph (coverage blurred on the CPU in target pixels, cached under the blur); colour glyphs keep their colours and take only the paint's alpha. Blur radius is twice the standard deviation, as Skia's `radius / 2`; shadow opacity is ignored, as Skia ignores it.
- `FontFace2D` is not thread-safe (it sets its own FreeType size on the shared face as it rasterises), and a glyph is forgotten only when its atlas page is cleared.
- Web fonts (`@font-face`, `@font-palette-values`, `@font-feature-values`) load through the host's `LoaderStrategy` via `CachedFont`. `DocumentFontLoader` starts a load when text first needs it; until it arrives text is laid out in the fallback (invisible during the block period, visible after, per `font-display`, on the event loop's timers), then the selector invalidates the document's fonts and the page lays out again. WOFF 2 decodes through the `woff2` vcpkg port (with brotli) and WOFF 1 through zlib (`Graphics/WOFFFileFormat`). `FontCustomPlatformData` makes a FreeType face from a copy of the file's bytes, because a FreeType face owns its memory. `FileLoaderStrategy` knows `.ttf`, `.otf`, `.ttc`, `.woff` and `.woff2`. The CSS font face classes keep upstream's names (`CSSFontFace` and so on).
- The OpenType MATH table is read through HarfBuzz (upstream's `USE(HARFBUZZ)` branch), and `Font::MathData` remembers that it looked even when the font has no MATH table.
- Locale support is over ICU (`LocaleICU`, `PlatformLocale`, `DateTimeFormat` over LDML formats). ICU reads UTF-8 in place; a text with a prior context is copied after the context into a buffer the iterator owns.
- Chrome is the reference for right-to-left behaviour where upstream differs. Bidi text drawn outside the line layout uses `GraphicsContext::DrawBidiText`.

### Images and resources

- The host seam for loading is a `LoaderStrategy` (set through `PlatformStrategies::SetLoaderStrategy`; without one, loads fail). `LoadResource(frame, request, options, completion)` calls back once, at any time, with a `LoadedResource` (response and whole bytes) or a `ResourceError`, and Booey queues the completion as a networking task. Booey never reads files or decodes for the GPU itself.
- Krystal.UI's `FileLoaderStrategy` implements only `file:` URLs and reports the MIME type from the file extension; it is Booey's loader unless the host sets another. `View::LoadFile` gives the document its file's URL so relative `url()`s resolve; `View::LoadHTML` takes an optional URL and cache policy.
- Main resources are substitute data, `about:`, `data:`, or loaded through the `LoaderStrategy`. Subresources load asynchronously through the same strategy and the memory cache, and the document's load event waits for its requests, style sheets and fonts. `data:` URLs are decoded in Booey.
- The loader cache is a trimmed port of upstream's: `CachedResource`, `CachedImage`, `CachedFont`, `CachedCSSStyleSheet`, `MemoryCache` (by URL, with capacities and pruning) and a `CachedResourceLoader` per document. `LocalFrame::SetSubresourceCachePolicy` is the host's per-document policy: it does not return to `Verify` after load, but the validated URLs (never cleared) keep a document from loading a URL twice. Revalidating reloads the resource, since file loads have no validators; the editor's F5 does so.
- Remote pages (an HTTP network loader with caching, cookies, origins and CORS) are out by choice: the host fetches remote data and pushes it into pages.
- Decoders are upstream's: `ScalableImageDecoder` with PNG, JPEG, WebP, GIF/APNG, BMP and ICO over a contiguous `SharedBuffer`. Decoded frames are `PlatformImage`s (in-memory ARGB). `BitmapImage` sniffs the format and decodes its frame when drawn or asked, caching the `NativeImage` and metadata. EXIF orientation sizes and orients drawing and patterns.
- Krystal.UI uploads each `NativeImage` once as a `BGRA8Unorm` texture (`ImageBufferTextures::Upload`, premultiplying if needed), keyed by rendering resource identifier; the texture is destroyed at the end of the first replay after the image is gone. Image buffers (display-list backed) render into pooled textures once per replay. `GraphicsContextRender2D` draws native images, image buffers and patterns with `DrawTexture` and `DrawTexturePattern`, applying orientation as Skia's context does. Krystal.UI's `TextureImage` is the base of engine textures and accelerated-buffer snapshots, drawn as their textures.
- Styles load pending images when renderers get them (`style::LoadPendingResources`: backgrounds, generated content, cursors, list markers, border images, masks, `shape-outside`). Renderers are the images' clients, so a load repaints (by scheduling a rendering update) or lays out what uses it. Images load only while the document has a render tree.
- SVG images are a page of their own per image (no frame tree), with `SVGImageChromeClient`, `SVGImageCache` and `SVGImageForContainer`; `CachedImage` picks them by MIME type. The theme's search field icons are `mask-image` SVGs drawn through this path.
- `<img>` selection (`srcset`, `sizes`, `<picture>`), `RenderImage`, `content: url()` and animated images (frame timers on the event loop; animation stops after its loops) follow upstream.

### SVG

- An `<svg>` is one replaced box (`LegacyRenderSVGRoot`) that paints its children itself; nothing inside it gets a layer. Only the legacy renderers exist.
- `SVGNames` and `XLinkNames` are `dom::QualifiedName` constants containing only names a ported file uses plus `class`, `id` and `style`. `SVGElementFactory` is a hand-written switch over `html::TagName`.
- `<use>` instances are shadow trees kept in step with their originals. `<foreignObject>` lays out HTML in SVG coordinates. Pending SVG resources live on the tree scope, so a `<use>` or `<textPath>` finds a target added later. SVG element changes lay their renderer out again at the next rendering update (`updateSVGRenderer`).
- Shape stroke geometry comes from the host: Krystal.UI implements `PathStrokeStrategy` (`PathStrokerStrategy`) with Render2D's stroker; Booey's tests use a stand-in (`TestPathStrokeStrategy`), and `NullGraphicsContext`'s line style setters can be overridden to collect the stroke style.
- Filter primitives run on the GPU through Render2D's `FilterGraph2D` and `FilterRenderer2D`; there is no software path.

### MathML

- MathML Core is the target, as in Chrome. `<math>` is an atomic inline box on its first line's baseline in the layout integration.
- STIX Two Math is bundled and is the `math` generic family (see Text and fonts). The MATH table is read through `OpenTypeMathData` over `hb_ot_math_*`, as upstream's FreeType and Skia ports do, rather than upstream's own table parser.
- Tests follow WPT's math fonts, copied under `Krystal.Booey.Tests/data/fonts/math/`.

### Canvas

- A 2D canvas's bitmap is an accelerated image buffer: whenever the host has an accelerated backend, every canvas uses it, whatever its size or `willReadFrequently`. Krystal.UI's `ImageBufferRender2DBackend` records drawing into a display list and, on each flush, renders what is new into a GPU texture it keeps, starting from the state the last flush ended with. Readbacks (`getImageData`, the encoders) flush and read the texture synchronously with `Device::ReadTexture`. Writes (`putImageData`) are drawn in as images in order with the rest. The rendering update flushes canvases before the view composites.
- The texture is made from the view's device on first render (`View::SetDevice` or the first paint) and freed with the backend or its view. Until then the buffer is transparent black and has no image. `AcceleratedImageBuffers` owns the page's canvas textures; `ImageBufferSnapshot`s keep retired textures until the next frame's commands have run.
- Without a host backend (Booey's tests) every buffer is a display-list backend: drawing is recorded and testable, and readbacks are transparent black.
- A canvas drawn into a canvas, or made into a pattern, is copied into a texture of its own at the call.
- `HTMLCanvasElement::GetContext` takes the type string only: `"2d"` and `"krystal-texture"` give contexts, and `"webgl"`, `"webgl2"`, `"webgpu"` and `"bitmaprenderer"` give nothing. A canvas is always a replaced element; its children are fallback content that does not render but stays focusable while the canvas is rendered and visible.
- `"krystal-texture"` shows a host-drawn texture: `EngineTexture` is the host's texture behind an interface (size, display delegate, image), and `EngineTextureRenderingContext` (a `GPUBasedCanvasRenderingContext`) shows it through `SetTexture`, which invalidates the layer composition, and `TextureChanged`, which maps a texture rect to the canvas and is its damage. `Reshape` does nothing: the host resizes. The texture must belong to the `gfx::Device` the view paints with; the host owns it, keeps it alive, draws into it before the view paints in the same frame, and its colours are sRGB-encoded. Its size is the canvas's natural size (300 by 150 by default), so CSS sizes and `object-fit` place it like an image. Booey sees only the abstract `EngineTexture`; Krystal.UI's `ui::EngineTexture::Create(texture, size, alpha)` wraps the `gfx::TextureHandle`. A context's pixels are a `NativeImage` (`SurfaceBufferToNativeImage`), so the texture draws without a copy.
- `font` resolves against the document's font selector through a `FontProxy`. Canvas `filter` is applied through `CanvasFilterContextSwitcher` and `CanvasLayerContextSwitcher` around each draw. `toBlob` calls back on a task on the canvas blob serialisation source.
- `CanvasRenderingContext2D`'s constructor is public, for `CreateUnique`.

### Editing and selection

- Selection and editing are WebKit's: `Position`, `VisiblePosition`, `VisibleUnits`, `TextIterator`, `VisibleSelection`, the document's `FrameSelection` and `Editor`, `RenderSelection`/`RenderHighlight`, and the DOM `Selection` (`Document::GetSelection()`, with its live range). There is one frame per document, so the `Document` owns its `FrameSelection` and `Editor`, and `Document::SetFocusedAndActive` stands in for the focus controller. `Settings::EditingBehaviorType` picks platform conventions (Windows by default).
- The selection's appearance is updated at the rendering update, which `FrameSelection::SetSelection` schedules through `LocalFrameView::ScheduleSelectionUpdate`. `selectionchange` is queued on the event loop's user interaction task source, once per task. `TemporarySelectionChange` reveals its selection itself, because `SetSelection` defers revealing to the rendering update and the temporary selection is gone by then; each reveal lays out again.
- Keyboard editing runs through the `Editor` and its `EditorCommand` table, after the page's `EditorClient` has had a chance to run a bound command. Krystal.UI's `EditorClient` keeps the undo and redo stacks (so the host can merge them with its own), holds the Windows key bindings and inserts the text of keypresses no binding handles. `Editor::HandleKeyboardEvent` and the client return whether the key was handled, as Booey's keyboard default handlers do, rather than setting `defaultHandled`.
- Typing goes through `TypingCommand`, which coalesces while the selection stays put. `beforeinput`/`input` (`InputEvent`) wrap edits and `textInput` (`TextEvent`) precedes typed and pasted text. `webkitBeforeTextInserted` lets text controls filter typed and pasted text.
- Mouse selection: a press places the caret, a drag extends, double and triple clicks select the word and paragraph, Shift extends, and dragging past an edge autoscrolls. `View::MouseMoved` carries the held button and drops moves that do not change position (Windows reports every press and release as a move), so a click does not select.
- Carets blink on the event loop's time with the theme's 500 ms interval (`SimpleCaretAnimator`); the blink stops while the mouse is down and the caret is hidden when the document is not focused and active. The block paints in its `caret-color`, and lines in a clipping editing host leave room for the caret at line ends.
- `HTMLInputElement` and `HTMLTextAreaElement` use user agent shadow roots, scroll to keep the caret in view, and keep masked passwords off the clipboard.
- Clipboard: `Pasteboard` and `PasteboardStrategy` are implemented by Krystal.UI's `SystemPasteboardStrategy` over Krystal.PAL (plain text as `CF_UNICODETEXT` with Windows line breaks, HTML, files, and a private format for pages' custom data). Copy and cut fire `beforecopy`/`copy`/`beforecut`/`cut`, paste fires `beforepaste`/`paste`, and pasted HTML goes through `WebContentReader` and `SanitizeMarkup`. Copying is allowed by default and script paste is off.
- Input methods: the host asks Booey about them through `EditorClient::SetInputMethodState()` and `Element::ShouldUseInputMethod()` (editable elements and text fields, not password fields), and `Editor::FirstRectForRange()` places the IME's windows. In Krystal.UI, `View::SetComposition()`, `ConfirmComposition()`, `CancelComposition()` and `InsertText()` apply the IME's changes; `AcceptsTextInput()` and `TextInputRect()` are polled; the view confirms the composition on a mouse, pen or touch press and when the window loses focus; and `SetCompositionDiscardedHandler()` tells the host to drop the IME's composition when the page ends its own. The window's input method is on only while the view shows and its focus takes text.
- Writing direction: `Editor::SetBaseWritingDirection` is what `View` calls for the Ctrl+Shift shortcut. A text field gets `dir` (firing `beforeinput` and `input`); an editing host's content is wrapped in a block taking `direction`.

### Input and events

- The host feeds mouse, wheel, key, pen, touch, text and composition input to `View` (Krystal.UI), which turns it into DOM events through the trimmed `EventHandler`. Every input method ends with a microtask checkpoint, and timers fire only from `View::Update`. Events from the user agent are trusted and bubble.
- Mouse: `mousedown`/`mousemove`/`mouseup`, `mouseover`/`out`/`enter`/`leave`, `click` at the nearest common ancestor (`auxclick` for other buttons; a `click` with detail 2 is followed by `dblclick`), hover and active chains, and the cursor (`EventHandler` computes it and the host reads it). `View` counts clicks. Mouse events are preceded by their pointer event, a cancelled `pointerdown` suppresses the compatibility mouse events until release, and `EventHandler::SetCapturingMouseEventsElement` sends mouse events to a capturing element (spin button, slider thumb).
- Pen and touch come from Windows pointer messages in Krystal.PAL (`PointerInput`, `OnPointer`); the mouse stays on its own messages. The system's press and hold and flicks are off, and a lost pointer is cancelled. `View::PenInput()` and `View::TouchInput()` deliver them (touch ids from the lowest free, every touch in each event); touches reach pages as touch events (`EventHandler::HandleTouchEvent()`) and pointer events. `GetPointingDevices()`/`SetPointingDevices()` feed the media features and `navigator.maxTouchPoints`.
- Gestures live in `View`, not WebCore: pan after a 10 px move (along the axes `touch-action` allows, after `pointercancel`) with fling, tap as a click of type `OneFingerTap` (double tap within 500 ms and 20 px), long press at 500 ms (`contextmenu` on lift) and two-finger pinch (page scale 1 to 5 about the midpoint). A right press or pen barrel button sends `contextmenu`.
- Keyboard: `keydown`, then `keypress` for keys that type text unless `keydown` is cancelled, then `keyup`, at the focused element or the body. The host sends combined key downs, which `EventHandler` disambiguates as on platforms without separate char messages. `input::Describe` gives a key's DOM `code`, name, legacy identifier and Windows key code. A press carries the characters `TranslateMessage` made for it (the queued `WM_CHAR`s); characters without a key press (emoji panel, Alt+numpad codes, an IME result outside a composition) arrive as `OnText`/`TextInputEvent` and type as a `keypress`. System keys carry no text, and `WM_SYSCHAR` is swallowed except for Alt+Space so Alt does not enter menu mode.
- Wheel events carry both axes in fractional notches with the cursor position and modifiers; `GetWheelScrollSettings` reads the system's lines and characters per notch (a line is 100/3 px).
- Focus follows the HTML specification in `HTML/Algorithms/FocusAlgorithms` (focusable areas, `tabindex`, focusing and unfocusing steps, focus delegates, autofocus, `FocusForClick`, `SequentialNavigation`, `DirectionalNavigation`), while hover, active and focus-within state follow WebKit (`UserActionElementSet`, `Document::UpdateHoverActiveState`). A page starts focused; `FocusAlgorithms::SystemFocusChanged` sets the focused-and-active flag from the window's focus, as Booey has no page activity state. A `mousedown` that is not cancelled focuses the nearest click focusable element (or the viewport); a click focus is not focus visible and a key press (not a modifier alone) makes focus visible. Tab and Shift+Tab are the default action of an uncancelled `keydown`.
- Spatial navigation is `FocusAlgorithms::DirectionalNavigation()`; `Settings::SpatialNavigationEnabled` (default off) makes arrow keys move focus and affects selects, radios and the caret.
- User activation (sticky, transient and history-action) is notified by presses and key presses other than Escape and consumed by APIs.
- Pointer lock: `PointerLockController` needs the window's transient activation and the host's answer through `View::SetPointerLockHandler()` (none means no pointer lock). It fails while the window lacks focus. Krystal.PAL's `IWindow::SetPointerLocked()` hides and confines the cursor (recentred after each move), reports accelerated and raw movement, and unlocks on focus loss; `View` forwards `LockedMouseMoved()`. Pointers cannot be captured while locked, and applying a lock releases their captures.
- Drag and drop: `View` runs the drag loop. Mouse moves over the page become `DragController` updates, moves off it leave, release drops, and Escape or losing focus cancels; Ctrl copies. Krystal.PAL captures the mouse while a button is held so a drag follows the mouse out of the window, and the cursor shows OLE's drag cursors. Drags in from other applications arrive through an OLE drop target on the window (`IDropTarget`, registered while the host has `OnDrag`) as `DragData`/`SelectionData` via `View::SystemDragInput()`; a drag carrying files is never offered a move.
- Gamepads: `GamepadProvider` is a host seam (default `EmptyGamepadProvider`) and the API is always on. Krystal.UI's `GamepadProvider` reads Krystal.PAL's pads (standard mapping, dual rumble) and the host calls `Update(now)` each frame after `Input::BeginFrame()`. `Gamepad` is the one `Modules/` API present. `View::GamepadInput(gamepads, now)` can also drive the page by direct calls rather than key events: D-pad or left stick moves focus spatially whatever the setting says (repeating after 500 ms, then every 100 ms), A clicks the focused element, B is a close request, the bumpers are Tab and Shift+Tab, the right stick scrolls, and an open overlay receives arrow keys, Enter, Escape and Tab instead. `SetGamepadNavigationEnabled()` turns it off.
- Krystal.PAL gamepad: triggers count as pressed past XInput's threshold (30/255), other buttons past half; sticks use XInput's radial dead zones rescaled to start at 0 with Y flipped to down positive. Connected slots are read each frame and empty ones once a second.
- Krystal.PAL's IMM32 side (`TextInput.hpp`) reports compositions as `OnComposition`/`CompositionInputEvent` (started, updated with clauses and caret in UTF-8 units, committed, ended). With a composition handler the IME's own composition window is hidden (candidates still show). `IWindow::SetTextInputEnabled()` starts off so games get raw keys; `SetTextInputRect()` places the candidate and composition windows. A key the IME took (`VK_PROCESSKEY`) is reported with `KeyText::HandledByInputMethod` and no text. `ProcessMessages()` dispatches all of the thread's messages so the windows the IME and text services keep on it work.

### Loading, navigation and history

- `LocalFrame` is a thin owner of the document and view plus the page and text zoom factors; the host creates frames and gives them documents. `Page` owns the main frame and runs the rendering update, which the host triggers once a frame (`ScheduleRenderingUpdate`, `UpdateRendering`, not reentrant). Its steps run in the specification's order: flush autofocus candidates, resize, scroll, media query evaluation, animations and animation frame callbacks, layout, focus fixup (focus moves to the viewport when the focused element stops being focusable), cursor update. Steps asked for during an update after they ran go to the next. Frames without a page still work, without rendering updates.
- `View::Update(now, budget)` runs the event loop (due timers, then tasks with a microtask checkpoint after each until the real-time budget runs out), then the rendering update if scheduled, then gives the rest of its budget (at most 50 ms) to idle callbacks, and returns whether the update ran.
- Time is the host's: `html::EventLoop::Run(now, budget)` never reads the clock and ignores an earlier time; `Timer`, `ThreadTimers`, `ScheduleTask(timeout, source, steps)` and `NextWakeTime()` run on it. Timers started while timers fire (or restarted) wait for the next run even if due, so a zero-delay self-restarting timer cannot spin. There is one task queue, process-wide. Style recalc and layout (0 s), the matched declarations cache sweep (a minute after the 100th addition), the font cache purge, scroll-to-focused-element, scrollbar autoscroll and `AbortSignal.timeout()` all run on these timers. The editor runs the page on its own time (summed frame deltas). A scheduled layout stays pending until the host runs it.
- `MediaEnvironment` is split: what upstream's view owns (layout size, media type, pagination) belongs to `LocalFrameView`; the rest (screen, pointing devices, user preferences, device scale factor, scripting, display mode) is a host-filled struct held by the frame (`GetMediaEnvironment`/`SetMediaEnvironment`) standing in for the page and its chrome client. The host must report environment changes to `MediaQueryList`s through `EvaluateMediaQueriesAndReportChanges`. Any change is treated as a style sheet environment change, and a device scale factor change rebuilds all style. A frame with no view has no media type, so queries other than `all` do not match.
- Every navigation (links, forms, `window.open`, `Location`, reloads) goes through `FrameLoader`, which asks `LocalFrameLoaderClient` for a policy (`DispatchDecidePolicyForNavigationAction` with a `NavigationAction`). Krystal.UI exposes this as `View::SetNavigationHandler`, which receives a `NavigationRequest` (URL, target, whether it opens a window or is within the page, source element, button, modifiers, `download`, window features, and a form's method, content type and body) and answers `Allow` or `Ignore`; a view without a handler allows everything. A new window is the host's to open: the client answers `Ignore` and `window.open()` returns null. `Page::Create` and `LocalFrame::Create` take the loader client (`EmptyFrameLoaderClient` ignores navigations).
- Loading is fully asynchronous. `View` has `Load`, `LoadFile`, `LoadHTML`, `Stop`, `Reload`, `IsLoading` and `SetLoadHandler` (started, committed, finished, failed), and starts with an initial empty document. Host markup is delivered as substitute data on a later task, and `View::LoadHTML` returns before the new document exists (tests run `View::Update` until `WaitForLoad`/`WaitForCommit`). A failed load leaves the old document in place.
- Form submission goes through the loader (`application/x-www-form-urlencoded`, `multipart/form-data` and `text/plain`, UTF-8 only) and reaches the host as a navigation request.
- Document lifecycle: the end of parsing sets `readyState` to `interactive`, fires `DOMContentLoaded` (bubbling to the window), then `complete`, `load` at the window (targeting the document) and `pageshow`. `Document::Parsing`, `IncrementLoadEventDelayCount` and `LoadEventFinished` drive this; style sheets, images, fonts and requests delay `load`, and pending head style sheets hold back rendering through the tree resolver.
- Unloading: `FrameLoader::ShouldClose` fires `beforeunload`, and the host confirms through `ChromeClient::RunBeforeUnloadConfirmPanel` (`View::SetBeforeUnloadHandler`) when the page asks to stay and has sticky activation. `pagehide` and `unload` fire as the new document commits, with no dialogs.
- Session history: `HistoryItem` (which keeps the host's markup), the page's in-memory `BackForwardList` through `BackForwardClient`, `BackForwardController` and `HistoryController`. An item is added for each new load and fragment navigation and replaced for reloads, same URL, `location.replace()` and redirects within a second. Scroll positions and form state are saved on leaving and restored after first layout. Krystal.UI exposes `GetBackForwardList`, `CanGoBack`, `CanGoForward`, `GoBack`, `GoForward`, `GoToItem`, `Reload`, the mouse's back and forward buttons and Alt+Left/Right unless the page handles them.
- Back/forward cache: `BackForwardCache` (size set by the host; views keep 3 pages), `CachedPage`, `CachedFrame`. A page that is left is kept suspended and detached (`pagehide` persisted, no `unload`) and restored at once (`pageshow` persisted, same document, scroll position). Eligibility: not the initial empty document, a current history item, no quick redirect coming, nothing loading, the client's `CanCachePage`, no `unload` listener, no `beforeunload` that asks, and not a reload, same load, redirect or replacement. Suspension (`Document::Suspend`/`Resume`) makes `EventLoop` tasks that name their document (`QueueTask(TaskSource, Document &, Steps)`) wait, keeps timers' time left (new timers in a suspended document start suspended), and stops animations and layout; a stopped document's tasks are dropped. A document leaving its frame stops its timers and drops callbacks unless cached.
- `History` and `Navigation` are usable from C++: `pushState()`, `replaceState()`, `go()`, `popstate`, and `Navigation` (`entries()`, `navigate()`, `intercept()` committing without a load, `traverseTo()`, `currententrychange`, `navigatesuccess`/`navigateerror`). Entries are kept across documents of the origin and restored with a cached page. State is a `RefPtr<SerializedScriptValue>`; promises are `NavigationPromise`s whose callbacks run as microtasks, and an `intercept()` handler is a `NavigationInterceptHandler` given a completion to call. A host load is a push (or replace), so the next document takes over the entries, and `View::Stop` aborts an ongoing navigation.
- `NavigationScheduler` handles meta refresh (after the document has loaded), location changes, form submissions and refreshes.
- Fragment navigation: an allowed navigation to a fragment makes the element it indicates (by id, then `<a name>`, then percent-decoded) the target (`:target`), scrolls it to the top of the view (`#top` and `#` go to the page top) through `LocalFrameView::ScrollToFragment`, focuses it (or the viewport) and makes it the sequential focus navigation starting point, and fires `hashchange` at the window. The view keeps the target in view through later layouts until a programmatic or user scroll clears it. A document opens at its URL's fragment when its parser stops or its pending style sheets load. Text fragments (`#:~:text=`) go through `LocalFrameView::ScrollToTextFragment`, which highlights, makes the nearest element the target, scrolls it to the centre and keeps it there, retrying for 3 s while the text is not there yet.
- Window members the host answers, each through a `View` handler: `focus()` (`SetFocusRequestHandler`), `close()` (`SetCloseRequestHandler`), window rectangle (`SetWindowRect`, `SetWindowRectRequestHandler`), alerts, confirms, prompts, print and console messages (without a handler alerts show nothing and prompts are cancelled), the user agent (`SetUserAgent`, otherwise `DefaultUserAgent`), and protocol handlers (`SetProtocolHandlerRequestHandler`). `ChromeClient` carries these requests, `LocalFrameLoaderClient` supplies `UserAgent`, `CanCachePage`, `ShouldGoToHistoryItem`, `DidRestoreFromBackForwardCache` and the load notifications, and `LoaderStrategy::IsOnLine` supplies network state. A window is made as its document becomes a frame's (`DidBecomeCurrentDocumentInFrame`); a document keeps its window after leaving its frame.
- Storage: `StorageArea` is the host's interface. `StorageProvider` (from `PlatformStrategies::GetStorageProvider`) gives local areas, with `MemoryStorageProvider` as the default and Krystal.UI's `FileStorageProvider` writing one file per origin (read on first use, written on each change). Session storage belongs to the page (`Page::SessionStorageArea`) and is in memory. `Storage` broadcasts changes to the other fully active windows of the origin using the area.

### Core and infrastructure

- **Settings.** `Page/Settings.hpp` holds the host's switches for features without a specification, the embedder features, and the values style resolution reads; standard features have no switch and are always on. Documents share the default settings unless the host gives them their own. Values upstream reads from `Settings` that Booey doesn't expose are upstream's defaults written in code (MathML Core's `CoreMathMLEnabled` and `CSSMathDepthEnabled`, for instance, are on).
- **XML.** libxml2 (vcpkg, without iconv or zlib) parses XML documents, which arrive decoded as UTF-8. External entities and DTDs never load. `DOMImplementation::CreateDocument` makes XML documents for XHTML, SVG and other XML types, and HTML documents for everything else (there are no text, image, media or plug-in documents). `DocumentParser` is only the XML parser's base; the HTML parser is `html::HTMLDocumentParser`.
- **Libraries.** ICU (`uc` and `i18n`; `uc` is public because `FontDescription.hpp` exposes `UScriptCode`) for breaking, bidi, case folding and locales; HarfBuzz and FreeType for text; `woff2`, `brotli` and `zlib` for web fonts; libxml2 for XML; brigand for type lists.
- **Krystal.Core** holds what isn't web-specific: the containers and pointers in the translation rules, the typed colour maths (`Colour/`), `StringBuilder`, `TextStream`, `Base64` (decoding only), `RefCounted` with resumable counts, `TriState`, and `text::Decode`, which strips a leading byte order mark.
- **Krystal.PAL** is the platform layer: windows and input, the clipboard (text, HTML, files read through `CF_HDROP`, and application formats), OLE drag and drop (initialised by `pal::Initialise()`), IMM32 text input, and gamepads. The clipboard, OLE and IMM32 paths have no automated tests: they need the system clipboard, another application or a real IME.
- **Benchmarks.** Hidden `[.benchmark]` cases in `Krystal.UI.Tests/tests/Benchmark.cpp` time `Update`, painting and submitting the editor page. Debug builds are much slower than Release.
